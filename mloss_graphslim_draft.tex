\begin{abstract}
GraphSlim is an open-source Python library for graph reduction built on PyTorch
and PyTorch Geometric. It brings sparsification, coarsening, and condensation
into a common workflow for constructing and evaluating reduced graphs. The
development version described here registers 40 methods and connects dataset
loading, reduction, checkpoint storage, and downstream training through shared
interfaces. Users can change the reducer or downstream model while reusing the
surrounding experiment code, or use individual components in their own workflows.
The library includes experiment planners, regression tests, and documentation of
method-specific settings and implementation differences. Source code is available
under the MIT license at
\url{https://github.com/Emory-Melody/GraphSlim}.
\end{abstract}

\begin{keywords}
graph reduction, graph condensation, graph coarsening, graph sparsification,
open-source software
\end{keywords}

\section{Introduction}

% Opening: the task and the practical problem faced by a user.
Graph reduction aims to retain useful information in fewer nodes or edges.
Sparsification selects existing nodes or edges, coarsening combines nodes into
groups, and condensation constructs a small synthetic training
graph~\citep{hashemi2024comprehensive}. These approaches offer different tradeoffs
between graph size, construction cost, structural fidelity, and predictive
performance. To compare them, a researcher needs to control the data split,
preprocessing, reduction budget, and downstream learner as well as the reduction
algorithm itself.

% Contribution: the software mechanism that addresses the problem.
GraphSlim brings these steps into one Python workflow. A dataset loader prepares
the graph and its splits, a method factory constructs the chosen reducer, and an
evaluator trains a downstream model using the saved reduced representation.
The same components serve the command line, Python API, and benchmark scripts.
This design lets users compare a simple selection baseline with a coarsening or
condensation method without maintaining a separate training script for each.

% Positioning: place the package in the graph-learning software ecosystem.
GraphSlim builds on the graph representations and operators of PyTorch
Geometric~\citep{fey2019fast} and uses dataset sources including the Open Graph
Benchmark~\citep{hu2020ogb}. Its focus is the reduction and evaluation workflow.
The package exposes both a complete training entry point and individual loader,
reducer, and evaluator components. Users can therefore run a configured
experiment or incorporate graph reduction into their own training code.

\section{Design and Method Coverage}

% Design: explain the data contract in terms of concrete inputs and outputs.
GraphSlim separates dataset preparation, reduction, and evaluation
(Figure~\ref{fig:workflow}). A shared data object, \texttt{TransAndInd}, holds features,
adjacency, labels, and train/validation/test indices, together with the
corresponding subgraphs. Reducers accept this object and a verbosity flag in their
\texttt{reduce} method. They store
the reduced features, adjacency, and training targets as \texttt{feat\_syn},
\texttt{adj\_syn}, and \texttt{labels\_syn}. The evaluator loads this representation
from checkpoints. An edge sparsifier can retain the original node set; a
coarsener or condensation method can instead change the number of training
nodes. Sharing these fields does not require the algorithms to share an
objective or optimization procedure.

% Breadth: counts are taken from the local registry, excluding aliases.
The method registry contains 40 canonical entries
(Table~\ref{tab:methods}); aliases are not counted as additional methods.
It imports implementation classes when they are requested, so method discovery
does not load PyTorch or optional algorithm dependencies. Each entry specifies
the implementation class and reduction family. To add a reducer, a developer
implements the constructor and reduction interface, writes the three checkpoint
tensors, and adds a \texttt{MethodSpec} entry to the registry. Existing loaders
and evaluators can then be reused. Method settings remain configurable because
different algorithms require different training and preprocessing budgets.

% Scope: extensions are adaptations, with explicit mathematical boundaries.
CGC, ClustGDD, GCGP, and NOPE use the same interfaces as the existing methods.
Their documentation gives source references, parameter profiles, and adaptation
details. For example, GCGP saves continuous training targets and uses a
compatible downstream regression loss; NOPE retains a mapping to coarse nodes
and reports the achieved node budget. These distinctions matter when comparing
outputs with those of the original implementations. The adapters do not by
themselves establish reproduction of the original papers' accuracy or runtime.

\section{Usage and Evaluation}

% Usage: resolve arguments before constructing the dataset or reducer.
The following Python example runs node selection on Cora using a CPU:
\begin{verbatim}
from graphslim.config import get_args
from graphslim.train_all import run

args = get_args([
    "-D", "cora", "-M", "kcenter", "-G", "-1", "-R", "0.5",
    "--run_reduction", "1", "--run_eval", "3",
    "--eval_epochs", "300", "--save_path", "./checkpoints",
])
scores = run(args)  # one (mean, standard deviation) per reduction
\end{verbatim}
The same options are accepted by \texttt{graphslim-train}. Replacing
\texttt{kcenter} with \texttt{gcond} changes the reducer; \texttt{--eval\_model}
selects the downstream architecture. For custom orchestration, users can call
\texttt{get\_dataset}, \texttt{create\_reducer}, and \texttt{Evaluator} directly.
Configuration files supply method defaults, and explicit command-line options
take precedence.

% Protocol: specify what the returned scores and budget actually mean.
Reduction budgets must be interpreted with the selected method. For node
selection and condensation, \texttt{-R 0.5} targets half of the labeled training
nodes, with per-class rounding; it does not request half of the full graph.
Edge sparsification uses an edge budget, while some coarseners can produce a
different achieved node count. The evaluator supports GCN, SGC, APPNP, Cheby,
GraphSage, GAT, and SGFormer. It selects downstream weights on validation data
and returns the mean and population standard deviation of test scores across
\texttt{run\_eval} fits of the same reduced graph. Repeated reductions use
separate seeds and yield separate summaries.

% Reproducibility: distinguish a planner and stored measurements.
The experiment planner generates commands for performance,
scalability, initialization, transferability, architecture search, graph
properties, and robustness. A \texttt{--dry-run} prints the planned commands.
The repository keeps published reference values separate from local measurements
and records source versions, splits, seeds, and settings for the latter.
Missing scores remain explicit. A shared API makes experiments easier to
orchestrate, but comparisons still require matched data and evaluation
protocols; different preprocessing or training budgets can change the result.

\section{Testing, Availability, and Limitations}

% Evidence: software tests and a bounded real-data integration report.
Regression tests exercise configuration precedence, method discovery, entry
points, split handling, checkpoint loading, and downstream optimization on
small graphs. The repository defines Ubuntu CPU continuous-integration jobs
for Python 3.10 and 3.11, including tests, documentation builds, and package
builds. A stored Cora integration report covers CGC, ClustGDD, GCGP, and NOPE under
eight training conditions with seven downstream architectures: 32 reductions
and 224 downstream fits. This report uses a short smoke profile to check
integration and records its source snapshot. It is evidence that these paths
ran, rather than an estimate of benchmark accuracy or a validation of every
registered method on every dataset.

% Availability: current checkout and published wheels are different scopes.
GraphSlim is distributed under the MIT license.\footnote{An earlier software
version accompanied a node-classification benchmark~\citep{gong2025gc4nc}.
Differences between versions are recorded in the repository document
\texttt{docs/mloss\_extensions.md}.} The source repository contains
installation instructions, tutorials, an API reference, and examples of node
selection, coarsening, condensation, and custom settings. Released packages
are available on PyPI. The development code described here requires Python
3.10 or 3.11; its examples should be run from that source checkout. Installation
requires PyTorch and matching PyG extensions, \texttt{torch-scatter} and
\texttt{torch-sparse}. DGL dataset support, experiment tracking, visualization, and fuzzy
clustering have optional dependency groups. The core workflow does not require
an external tracking service.

% Limitations: actual scope and costs, without a generic future-work list.
The current workflow focuses on node classification. Method support and resource
requirements vary: trajectory-based condensation needs expert buffers, kernel
methods can require dense computations, and learned adjacency can consume
quadratic memory in the reduced node count. Reducing a graph also has a cost,
so a smaller training set does not guarantee lower total runtime. The software
contribution is a common place to implement, run, and inspect these tradeoffs.
